# ADR 0002 · 默认路由：按风险升级，而不是永远全编排

- **状态**：已采纳（2026-10-28）
- **影响面**：`app/orchestrator/routing.py`、`Pipeline.run`、`config.routing_policy`、缓存键

## 背景

三配置对照（`REPORT.md` §9）测出的事实：

| | 引用命中 | 金额准确率 | LLM/题 | 中位延迟 |
|---|---|---|---|---|
| 单 Agent | 0.741 | 0.667 | 1.00 | 2.6s |
| 全编排 + 五道闸 | 0.771 | 1.000 | 3.62 | 7.6s |

即：**全编排在单跳规则问答上只多 3pt 引用命中，却贵 3.6 倍、慢 3 倍**；
它的真正价值集中在"要算钱"（+33pt）和"引用必须可核验"这两类场景。

如果默认对所有问题跑全编排，等于让 80% 的简单问题为 20% 的复杂问题付账。
这不是架构问题，是**产品定价问题**。

## 决策

默认策略 `ROUTING_POLICY=auto`：**用规则判断风险，按风险选档**。

| 判据（全部来自规则，零 LLM） | 档位 |
|---|---|
| 需要金额测算 | `full` |
| 多跳（计划里有 ≥2 路检索） | `full` |
| 合规审查（企业方 / 制度条款） | `full` |
| 其余（单跳规则问答） | `fast` |

`fast` 的含义不是"不校验"，而是：

- **不调 LLM 分诊**（用规则分诊，事实槽位在单跳规则题里不需要）
- **不跑 G4**（语义支撑判定要一次 LLM）
- **没有补检索回路**
- **仍然跑 G1/G2/G3/G5 + 引文自动对位**（四道零成本闸）

于是 `fast` 的承诺是：**一次 LLM、2 秒级、引用仍然被确定性校验过**。

## 为什么判据必须用规则而不是 LLM

顺序反了就没意义：若先用 LLM 分诊再决定"要不要走廉价通道"，
省下的那次调用又被分诊吃了回去。所以 `Pipeline.run` 的顺序是：

```
规则分诊（零成本） → 定档 → fast 就直接用规则结果；full 才调 LLM 分诊
```

代价是 `fast` 档没有事实抽取能力——但单跳规则题本来就不需要槽位；
需要槽位的题（要算钱）必然被判进 `full`。这条依赖是闭合的。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 永远全编排 | 实测 3.6 倍成本换 3pt，不划算；延迟也过不了 2s 的交互门槛 |
| 永远单 Agent | 金额准确率掉 33pt，法律场景不可接受 |
| 用 LLM 判断复杂度再选档 | 省下的调用被分诊吃掉，净成本反而更高 |
| 按用户等级/付费档位选 | 与问题风险无关，会把"该算的钱"算错 |

## 后果

- **正面**：默认路径回到 1 次 LLM；复杂问题仍走全编排。路由理由进 `meta` 事件，可解释。
- **负面**：多了一个配置项和一处分叉，测试要覆盖两档（`tests/test_routing.py` 11 条）。
- **已知缺口**：判据仍是粗粒度关键词/计划形状，不是学出来的。
  下一步可以用评测数据拟合一个轻量分类器，但**必须先有足够样本**（当前 49 条，不够）。

## 回退方式

```bash
ROUTING_POLICY=full python -m app.runtime ask "..."   # 一键回到永远全编排
```

`--policy fast|full` 也可单次覆盖。这是刻意保留的开关：
出问题时应能一行配置退回已验证的形态。
