# 06 · 金额评测集（30 条）的口径与边界

金额是本项目唯一"确定性优于模型"的硬结论，所以它的评测集必须比法条集更严：
**金标是算出来的，不是记出来的。**

## 1. 为什么这条评测集可信

| 环节 | 做法 |
|---|---|
| 出题 | 手写题面（真实日期、当事人措辞），**不手写答案** |
| 金标 | 由 `app/calc/engine.py` 独立算出，写进 `expected_value` |
| 核对 | `python -m scripts.check_calc_gold` 用引擎回算 30 条，与金标逐条比对 |
| 冲突处理 | **不自动以引擎为准**，人工判断是金标错还是引擎错 |

这条纪律抓到过一次真实错误：c25（2 年 9 个月）我最初按 N=2.5 写，
引擎算出 N=3 —— 因为"余 9 个月 ≥ 6 个月按 1 年计"。金标错了，引擎对。
如果当时改成"以引擎为准自动覆盖"，这个错误会被掩盖，而且以后引擎真错时也发现不了。

## 2. 覆盖矩阵（8 类公式 × 3 条起）

| 类型 | 条数 | 覆盖的边界 |
|---|---|---|
| severance（N） | 8 | 余 ≥6 月按 1 年 / 余 <6 月按半月 / 月末入职 / 刚好满 1 年 / 8 年以上 |
| illegal（2N） | 4 | 短工龄（10 个月）/ 半年线两侧 |
| notice（+1） | 3 | 未提前通知 / 保留到分 |
| overtime | 4 | 三种倍数单测 / 混合加班 |
| double_wage | 3 | 11 个月封顶 / 6-8 个月 |
| annual_leave | 4 | 300% / 1 天（分位舍入） |
| non_compete | 4 | 30% / 低工资 / 高工资 |
| probation | **0** | 单位是"月"不是金额，**不纳入金额评测**（见 §4） |

## 3. 一个必须说清的取舍：题目纯度

c15 最初写成"没有提前通知，除了经济补偿还能拿代通知金吗？多少？"。
系统答"还需要你补充：离职日期、入职日期"——**这是正确行为**，
因为经济补偿确实需要起止日期，而题面没给。

问题在题面同时问了两件事，导致"答不出来"无法归因。改成纯代通知金问题（只需月薪）后，
四档全部答对。**结论：一个题目只能考一个能力**，否则失败无法定位。

## 4. probation 为什么不进金额集

`probation` 算的是"试用期上限几个月"，输出单位是月，不是元。
把它塞进金额准确率会污染分母（拿"3 个月"和"72000 元"比较没有意义）。
它由 `tests/test_calc.py` 的边界用例覆盖，不参与跨配置对照。

## 5. 30 条样本的统计效力

* 单题权重 3.3%（原 9 条时是 11%）；
* A 档 17/30 = 0.567，95% CI [0.40, 0.73]；B/C/D 是 30/30，CI [1.00, 1.00]；
* **两个区间不重叠**，所以"确定性引擎把金额准确率从 57% 拉到 100%"这条结论可读。

但仍要注意：**30 条覆盖不了"未知公式"**。引擎只算它认识的 8 类，
遇到第 9 类（比如工伤赔偿、经济补偿的分段计算）会报缺槽位或直接不支持——
这部分能力边界不在评测集里体现，属于**评测集的盲区**，不是系统的优点。

## 6. 复现

```bash
python -m scripts.check_calc_gold                  # 30/30，零调用
python -m eval.compare_agents --set calc --reuse   # 四档金额表
python -m eval.compare_stats --set calc            # 带 95% CI
```
