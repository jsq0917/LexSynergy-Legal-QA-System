## 1. 六个决策的定论与理由

### Q1 用户角色：双角色（劳动者 + 企业 HR/法务）✅

**理由**：`role` 是编排层唯一能低成本获得的"上下文作用域"维度。LangGraph 社区总结的拆分判据是「不同工具 / 不同上下文 / 不同产物类型」——企业角色会触发 `ComplianceAgent`（产物是 issue list，不是答案），劳动者角色不触发。没有这个维度，ComplianceAgent 就只能靠关键词猜，而关键词猜不准是这类系统的通病。
**代价**：多一套 8 条审查用例。可接受。

### Q2 判例语料：不做，用司法解释 + 地方裁审口径替代 ✅

**理由**：判例（裁判文书）有三个硬问题：① 获取与清洗成本远超收益（去标识、段落结构不统一、同一案由表述差异极大）；② 判例的"说理"**不能当法条引用**，一旦被引用就会污染引用校验的准确性；③ 中国不是判例法国家，援引价值弱于成文法。
**替代**：最高人民法院《劳动争议司法解释（一）（二）》+ 8 条地方裁审口径（如上海、北京关于加班费基数），它们有明确文号、可像法条一样做存在性与原文一致性校验。

### Q3 A2A 实现：**官方 `a2a-sdk`**（推翻草案）⚠️

草案建议自研 200 行异步兼容层，理由是"参考项目用的 `python-a2a` 是 Flask 同步底座，导致事件循环冲突"。**这个理由成立，但结论错了**——因为冲突来自 `python-a2a`，不是来自 A2A 生态。

核实结果：官方 `a2a-sdk` 是 **Starlette + async** 架构，核心接口就是两个 async 方法：

```python
class AgentExecutor:
    async def execute(self, context: RequestContext, event_queue: EventQueue) -> None: ...
    async def cancel(self, context: RequestContext, event_queue: EventQueue) -> None: ...
```

也就是说，参考项目花大力气绕开的"同步 handler 里 `asyncio.run`"问题，在官方 SDK 里**根本不存在**。选它的三个理由：

1. **协议合规**：Agent Card 自动挂在 `/.well-known/agent-card.json`，可以用 `curl` 验证、可以被任意 A2A 客户端发现。自研层做不到"别人真的能接进来"。
2. **可测性不打折**（关键）：把业务逻辑放在 executor **之外**的纯 async 类里（`StatuteAgent.run(req)`），executor 只做 10 行协议适配。测试直接调 `run()`，不需要构造 `RequestContext/EventQueue`，也不需要启容器。**这正是草案想要的"双传输"效果，而且不用自己造协议。**
3. **结构化产物有协议支持**：`DataPart` 天然承载 JSON，把 `AgentResult` 塞进 `Part(root=DataPart(data=...))`，从协议层面消灭参考项目"artifacts 有 str 有 dict"的坑。

**风险与兜底**：SDK 版本演进快（0.3 → 1.0 有兼容层）。P1 第一件事是跑通官方 helloworld，用 `curl` 确认 card 路径与字段名，再动手改；`pyproject.toml` 锁精确版本，升级单独一个 PR。**如果 1 天内跑不通，回退到草案的自研层**——回退成本只是 200 行，不影响其余设计。

### Q4 前端：复用 LawAnswer 6 页，只加两个组件 ✅

**理由**：前端不是这个项目的差异化点，重写纯属浪费时间。复用 `ChatView` 的 SSE 消费逻辑（`useSSE.ts`）+ 新增「协作时间线」抽屉与「证据表格」。这两块恰好是 demo 时最抓眼的：能看见"系统先查了什么、谁在什么时候返回了几条证据"。

### Q5 编排框架：**不用 LangGraph**，自写 DAG，但抄它的四条约束 ✅

不用的理由：① 项目卖点是"协议分层 + 服务边界"，LangGraph 把 4 个 Agent 降级成图节点，与"可独立部署"的叙事直接冲突；② 编排层实际只需要 DAG 拓扑 + 并行 + 回路 + checkpoint，约 300 行；③ 多一个框架就多一层调试面。

但**必须抄它四条被生产验证过的约束**（这是"参考成熟做法"的实质）：

| 借鉴项 | LangGraph 社区的做法 | 我们的落地 |
|---|---|---|
| 路由决策结构化 | supervisor 用 `with_structured_output` 只返回 `{next, reason}`，不做聊天 | Planner 返回 `Plan{steps[], reason}`，Pydantic 校验，非法即回落规则路由 |
| 递归/步数硬上限 | 新版默认 `recursion_limit` 已不是 25（实测取环境变量，缺省上万），必须显式设 | `MAX_STEPS=8`、`MAX_LOOP=1`、`GLOBAL_DEADLINE=25s` 三道闸 |
| checkpoint + thread_id | 每步落盘，进程挂了可续跑；调试可回放 | `task_steps` 表按 `(task_id, step_id)` 落 checkpoint，支持 `--resume` |
| worker 不互调 | 每个 worker 必须回 supervisor，否则 supervisor 看到的历史不是事实 | 专家之间零通信，全部经 Orchestrator |

**额外一条来自实践的警告**（原话大意：若子 Agent 用同一模型、同一工具、只产出文本，就该合并成单 Agent 加长 Prompt）：这条正好是我们的自检标准——4 个 Agent 的工具集、产物类型、上下文范围全不同，通过检验。

### Q6 术语映射表：保留并扩 ✅

`term_map.py` 的价值是"确定性优先"：把"老板不给钱"直接映射到"拖欠劳动报酬"，比让 LLM 改写更稳、更快、可单测。**放在 Triage 之前做前置归一化**，命中即改写，未命中才交给 LLM。

### 三个最值得说的借鉴点（面试直接讲）

**① 用 SOP 而不是"功能列表"来划 Agent**
ChatLaw 的划分来自真实律所流程，不是"检索/计算/写作"的功能切分。功能切分会切出"检索 Agent 也顺便写两句"的越界；SOP 切分天然带职责边界与交接物（事实清单 → 证据清单 → 意见书）。我们的四专家 + 编排器就是这套 SOP 的工程化。

**② 把"必须正确的部分"全部交给代码**
legal-agent 的核心主张：法条是否存在、引文是否一字不差、当时是否有效、金额是否等于公式结果——这四件事**没有一件需要大模型**。大模型只负责把已核实的事实组织成中文。这直接决定了 Verifier 的设计：5 道闸里 **4 道零 LLM**，只有"语境支撑"用 LLM。这也顺带把校验成本压到几乎为零。

**③ 种子缺陷评测比"引用命中率"高一个量级**
LawAnswer 的 81.8% 是人工统计"答案里出现的条号覆盖了多少期望条号"，口径模糊、不可复现、且无法回答"误报率"。种子缺陷评测是：拿 40 条**正确**答案，程序化植入 8 类错误（编造条号、张冠李戴法名、改一个字的引文、引用已废止版本、金额算错、结论与条文相反…），看校验器能抓出几类、有没有误伤正确答案。**分子分母都受控，可复现，还能报误报率**。这是本项目评测的主指标。

## 4. 关键实现要点

### 4.1 Agent 分层：业务与协议解耦（最重要的一条）

```python
# app/agents/statute.py —— 业务核心，零协议依赖，可单测
class StatuteAgent:
    def __init__(self, search: StatuteSearchService) -> None:
        self._search = search

    async def run(self, req: StatuteRequest) -> AgentResult:
        hits = await self._search.search_many(req.sub_queries, req.law_hints, as_of=req.as_of)
        return AgentResult.ok(agent="statute", evidence=hits)
```

```python
# app/agents/server.py —— 协议适配，约 15 行，所有 Agent 复用同一个
class ExecutorAdapter(AgentExecutor):
    def __init__(self, agent, to_request, to_response) -> None:
        self._agent, self._req, self._resp = agent, to_request, to_response

    async def execute(self, ctx: RequestContext, queue: EventQueue) -> None:
        task = ctx.current_task or new_task_from_user_message(ctx.message)
        updater = TaskUpdater(queue, task_id=task.id, context_id=task.context_id)
        await updater.update_status(TaskState.working)
        result = await self._agent.run(self._req(ctx.message))
        await updater.add_artifact(parts=[self._resp(result)])   # DataPart，结构化
        state = TaskState.input_required if result.status == "input_required" else TaskState.completed
        await updater.update_status(state)

    async def cancel(self, ctx, queue) -> None:
        raise NotImplementedError
```

### 4.2 EvidenceLedger（证据账本）

```python
@dataclass(frozen=True)
class Evidence:
    eid: str                 # E1..En，由账本统一编号
    law: str
    article_no: str          # 第四十七条
    chunk_id: str
    quote: str               # 条文原文（用于逐字比对）
    score: float
    from_agent: str
    effective_from: date | None
    effective_to: date | None

class EvidenceLedger:
    def add(self, items: list[Evidence], *, agent: str) -> list[Evidence]:
        """按 law#article_no 去重（保留高分），编号 E1..En 后返回本次新增。"""
    def lookup(self, law: str, article_no: str) -> Evidence | None: ...
    def for_prompt(self, *, as_of: date, budget_chars: int) -> str:
        """过滤掉 as_of 时已失效的条文，按分数灌入预算，输出【资料N】《法名》·章节·第X条"""
    def conflicts(self) -> list[tuple[Evidence, Evidence]]:
        """同一 law#article_no 出现不同 quote → 标记冲突，以 MySQL 为准"""
```

三条纪律：**只增不改**（避免 Agent 互相覆盖）、**编号即引用**（答案里的 `E3` 必须能在账本里查到）、**超预算丢低分**（不让 Agent 自己截断）。

### 4.3 DAG 调度器（含回路与三道闸）

```python
async def run_plan(plan: Plan, ctx: TaskContext, ledger: EvidenceLedger) -> PlanResult:
    deadline = time.monotonic() + ctx.budget.deadline_s
    done: dict[str, StepResult] = {}
    while len(done) < len(plan.steps):
        if time.monotonic() > deadline:
            return PlanResult.partial(done, reason="deadline")
        if len(done) >= MAX_STEPS:
            return PlanResult.partial(done, reason="max_steps")
        ready = [s for s in plan.steps if s.id not in done and all(d in done for d in s.deps)]
        if not ready:
            raise PlanError("cycle_or_missing_dep")
        results = await asyncio.gather(*(dispatch(s, ctx, ledger) for s in ready),
                                       return_exceptions=True)
        for step, res in zip(ready, results):
            done[step.id] = StepResult.from_any(step, res)   # 异常转 FAILED，不抛
            save_checkpoint(ctx.task_id, step, done[step.id])  # 每步落库
    return PlanResult(done=done)
```

回路在 `Synthesize → Verify` 之后：

```python
verdict = await verify(draft, ledger)
if verdict.action == "refine_retrieval" and ctx.loop < MAX_LOOP:   # MAX_LOOP = 1
    ctx.loop += 1
    plan = plan.with_extra_queries(verdict.missing_hints)          # 只补检索，不重跑全部
    await run_plan(plan, ctx, ledger)
    draft = await synthesize(ctx, ledger)                          # 重写，不复用旧草稿
    verdict = await verify(draft, ledger)
if verdict.action != "pass":
    draft = degrade_to_no_data(draft, ledger)                      # 降级，不硬撑
```

**关键细节**：回路只重跑"检索 + 汇总 + 校验"，不重跑 Triage/Planner/Calc——否则成本翻倍且结果不稳定。

### 4.4 Verifier 五道闸

```python
async def verify(draft: Draft, ledger: EvidenceLedger, calc: CalcResult | None) -> Verdict:
    fails: list[GateFail] = []
    for cite in extract_citations(draft.text):                 # 正则抽 《法名》第X条
        if not (ev := ledger.lookup(cite.law, cite.article_no)):
            fails.append(GateFail("G1_not_found", cite)); continue      # 编造 / 断链
        if not verbatim_match(cite.quote, ev.quote):                     # 逐字比对（去空白标点）
            fails.append(GateFail("G2_misquote", cite)); continue
        if not effective_at(ev, draft.as_of):                            # 事发当时是否有效
            fails.append(GateFail("G3_expired", cite)); continue
    if calc and not numeric_consistent(draft.text, calc.value):          # 金额/年限
        fails.append(GateFail("G5_numeric", calc))
    unsupported = await llm_support_check(draft.claims, ledger)          # 唯一用 LLM 的闸
    fails += [GateFail("G4_misgrounded", c) for c in unsupported]
    ...
```

| 闸 | 查什么 | 对应错误类型 | LLM | 耗时 |
|---|---|---|---|---|
| G1 | 条号是否真实存在于库 | 编造引用 / 断链 | ✗ | <5ms |
| G2 | 引文与原文是否逐字一致 | 篡改引文 | ✗ | <5ms |
| G3 | `as_of` 时该条是否有效 | 引用已废止版本 | ✗ | <5ms |
| G4 | 该条是否支撑这句话 | **错误支撑（Mode 2）** | ✓ | 2–4s |
| G5 | 金额/年限是否等于公式结果 | 算错 | ✗ | <1ms |

`action` 三值：`pass` / `refine_retrieval`（G1/G3/G4 失败）/ `downgrade`（二次仍败或 G5 失败——金额错一律不改写，直接标红）。

### 4.5 checkpoint 与断点续跑

```sql
CREATE TABLE task_steps (
  task_id     CHAR(26) NOT NULL,
  step_id     VARCHAR(32) NOT NULL,
  agent       VARCHAR(32) NOT NULL,
  status      ENUM('ok','degraded','failed','skipped') NOT NULL,
  artifact    JSON NULL,
  elapsed_ms  INT NOT NULL,
  llm_calls   TINYINT NOT NULL DEFAULT 0,
  created_at  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (task_id, step_id)
);
```

`--resume <task_id>` 时先 `SELECT step_id` 把已完成的步骤标记为 done，调度器自动跳过。调试时可以把任意历史 task 重放一遍看它是怎么走偏的——这是 LangGraph `time travel` 的等价物，也是被追问"你怎么定位多 Agent 走错"时的答案。

### 4.6 缓存键（别沿用 LawAnswer 的单 sha1）

```python
def cache_key(q: str, role: str, plan: Plan, as_of: date) -> str:
    fp = sha1("|".join(s.id for s in plan.steps))[:8]      # DAG 指纹
    return f"ans:{sha1(normalize(q))[:16]}:{role}:{fp}:{as_of:%Y%m%d}"
```

不这么改会出现：同一个问题，劳动者问（走 Statute+Calc）和企业问（走 Statute+Compliance）命中同一份缓存答案。

## 6. 评测：主指标换血

### 6.1 主指标 —— 种子缺陷检出（借鉴 legal-agent）

**做法**：取 40 条**已人工确认正确**的答案，程序化植入 8 类错误，每类 5 条，共 40 条缺陷样本 + 40 条原答案（作对照组测误报）。

| # | 缺陷类型 | 植入方式 | 期望被哪道闸抓到 |
|---|---|---|---|
| 1 | 编造条号 | 把"第四十七条"改成"第一百四十七条" | G1 |
| 2 | 张冠李戴法名 | 劳动合同法第 39 条 → 劳动法第 39 条 | G1/G2 |
| 3 | 篡改引文 | 条文里删掉"额外支付一个月工资" | G2 |
| 4 | 引用已废止版本 | 换成 2008 年版表述，`as_of` 设为 2026 | G3 |
| 5 | 结论与条文相反 | 把"应当支付"改成"无需支付" | G4 |
| 6 | 金额算错 | 5.5 个月写成 5 个月 | G5 |
| 7 | 无依据建议 | 加一句"你可以直接申请查封公司账户" | G4 |
| 8 | 跨法拼接 | 把民法典条款混进劳动法结论 | G1/G4 |

**两个指标，必须同时报**：
- **检出率** = 被抓出的缺陷数 / 40（目标 ≥ 95%，即 38/40）
- **误报率** = 40 条正确答在被判 fail 的比例（目标 ≤ 5%）

> 只报检出率是耍流氓——把闸门调严到"什么都 fail"就能 100%。**双向度量**是 legal-agent 最值得抄的一条纪律。

### 6.2 辅助指标 —— 单 Agent vs 多 Agent 对照

同 60 条、同语料、同模型，六列对照：`Recall@5 / 引用准确率 / faithfulness / 金额准确率 / LLM 调用数 / P95 延迟`。

**用法**：不是证明"多 Agent 更好"，而是**说清"哪一类问题值得多 Agent"**。预期（待实测验证）：单点法条问题多 Agent 无收益甚至更慢；多跳 + 计算 + 审查三类有正收益。**如果实测结果相反，就照实写**——这种结论在面试里比"我的架构很先进"值钱得多。

## 7. 简历口径（据实填写，勿预设数字）

> **LexSynergy**：法律合规多智能体问答系统。参考 ChatLaw 的律所 SOP 划分专家职责，用官方 A2A SDK 将「法条检索 / 金额测算 / 合规审查 / 引用校验」四个专家做成可独立部署、独立降级的服务（其中两个不含 LLM，纯确定性），编排层自研 DAG 调度器（规则短路覆盖约 80% 请求、回路硬上限 1 次、每步 checkpoint 可续跑可回放）。核心增量是**五道引用校验闸门**：4 道零 LLM 的确定性检查（条号存在、引文逐字一致、as_of 时效、金额一致）+ 1 道 LLM 语义支撑检查，专门针对"引对了条文却支撑不了结论"这一主导性失败模式。以**种子缺陷评测**为主指标：8 类植入错误检出率 `__%`、误报率 `__%`；同 60 条样本的单/多 Agent 对照显示引用准确率 `+__pt`、多跳召回 `+__pt`，代价 P95 延迟 `+__ms`。

三个可直接讲的技术判断：
1. **为什么不用 `python-a2a`**：它是 Flask 同步底座，`handle_task` 必须是同步方法，要在异步编排里 `run_in_executor` + `asyncio.run` 绕事件循环——代价是每请求新建 loop、MCP 连接无法复用。官方 `a2a-sdk` 是 Starlette async，这个坑从根上不存在。
2. **为什么 Agent 里可以没有 LLM**：法条检索和金额测算都不需要语言模型做判断。把它们做成 Agent 是为了能力边界与独立降级，不是为了"看起来像多智能体"。业界判据是"工具集/上下文/产物类型是否不同"，不是"步骤是否不同"。
3. **为什么校验要 5 道而只查条号不够**：查条号只能挡 Mode 1（编造）。真实法律场景里更危险的是 Mode 2——条号真、引文真，但这句话不是这条法条的意思。2000 多起法院制裁案例里，主导失败模式是后者。
