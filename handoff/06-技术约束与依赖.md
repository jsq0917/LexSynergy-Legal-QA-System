## 二、模型

| 用途 | 模型 | 说明 |
|---|---|---|
| 文本生成（分诊 / 撰稿 / G4） | **`deepseek-v4.1-flash`** | 阿里云百炼，OpenAI 兼容端点 |
| 稠密检索（默认） | **bge-m3**（本地，1024 维） | 索引已建，换模型必须重建并重测 |
| 稠密检索（备选） | `qwen3.7-text-embedding-flash` | 无 torch 环境用，**向量不可互换** |
| 重排 | bge-reranker-v2-m3（本地，未接） | — |

端点：`https://dashscope.aliyuncs.com/compatible-mode/v1`（**不要带尾斜杠**）

### 必须知道的四个坑

1. **思考模式默认开启**：`max_tokens=16` 时 token 全进 `reasoning_content`，`content` 返回空。
   每个请求显式带 `enable_thinking: false`（33 token → 2 token）。
2. **`stream_options` 必须与 `stream=true` 成对出现**，否则 400。
3. **JSON 模式不保证 schema**：实测出现过键名改写（`intent` → `int#`）。
   所以字段逐个校验 + 规则回落，不可省。
4. **embedding 配额**：`text-embedding-v3/v4`、`qwen3.7-text-embedding` 可能报 `Free quota exhausted`；
   只有 `qwen3.7-text-embedding-flash` 实测可用。

## 三、环境变量（`.env`，已 gitignore）

```ini
# 编排
ROUTING_POLICY=auto            # auto | fast | full
REQUEST_DEADLINE_S=45

# 检索
RETRIEVAL_BACKEND=dense        # dense | hybrid | bm25
RETRIEVAL_TOPK=5
EMBEDDING_BACKEND=local        # local | dashscope
EMBEDDING_MODEL_PATH=          # 空 = HF 缓存里的 bge-m3

# LLM
LLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
LLM_MODEL=deepseek-v4.1-flash
LLM_MODEL_FAST=                # 空 = 复用
LLM_API_KEY=
LLM_ENABLE_THINKING=false       # 必须 false
LLM_TIMEOUT_S=35
LLM_RETRY_ON_TIMEOUT=false      # 超时不重试

```

优先级：**进程环境变量 > `.env` > 代码默认值**（`config.load_dotenv()` 不覆盖已有变量）。

## 四、Windows 特有的坑（重要）

### 1. 必须限制 BLAS 线程数

```bash
export OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1
```

不设会出现 `OpenBLAS error: Memory allocation still failed after 10 retries, giving up.`
并**直接段错误**（退出码 139）。这不是代码 bug，是 OpenBLAS 在内存紧张时的线程缓冲区分配失败。

**表现**：`import numpy` 都可能崩；稠密检索加载模型时崩。

### 2. 并发别开太高

评测并发建议 3–5。开更高会叠加上面的内存问题。

### 3. 路径

- 用绝对路径或从项目根出发；
- **不要用 `/tmp` 做备份**：Git Bash 的 `/tmp` 与 Windows Python 看到的不是同一目录。

### 4. 已有外部进程

机器上可能跑着数百个其他项目的 python 进程（例如某 `run_ab.py --arms` 会开出 600+ 个），
会吃掉 13GB+ 内存。**不要 kill 别人的进程**；发现内存不足先确认是不是这个原因。

## 五、冷启动（会导致"看起来像 bug"的行为）

bge-m3 首次加载 **6~20s**。这段耗时如果落进检索步的 20s 超时里，首个问题会答"检索超时"。

**已采取的措施**：
- API 侧：FastAPI `lifespan` 里**后台预热**检索器；
- CLI 侧：`app/runtime.py` 的 `_warmup_search()` **同步预热**。

**你应该知道的**：
- 首次 `ask` 会先打印"检索预热完成 20.7s"，然后才是问答耗时（约 3~4s）；
- 若你新增了别的入口（脚本、任务），**也要预热**，否则会复现同一个坑。

## 八、外部依赖风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 百炼 API Key 失效 / 欠费 | LLM 相关全挂 | `--no-llm` 可跑（规则分诊 + 模板撰稿 + 四道确定性闸） |
| bge-m3 权重不在本地缓存 | 稠密检索不可用 | 自动退回 BM25（`RETRIEVAL_BACKEND=bm25` 强制） |
| `a2a-sdk` 升级 | 协议层全断 | 已锁 0.3.22，升级前跑 `check_a2a_sdk.py` |
| 语料重建后条数不符 | 所有检索指标失效 | `build_corpus` 硬校验 98/107/1260，不符直接失败 |
